# AniDash Go device pairing

Website counterpart of Android Settings → Devices. Only the feature branch is changed.

## Deployment prerequisites
Configure these server-only environment variables for the intended Vercel environment:
- KV_REST_API_URL and KV_REST_API_TOKEN — automatically supplied by Vercel's Upstash integration (use the writable token, not the read-only token).
- Alternatively, set both UPSTASH_REDIS_REST_URL and UPSTASH_REDIS_REST_TOKEN. A complete explicit pair takes precedence; credentials are never mixed across the two configurations.
- DEVICE_PAIR_ENCRYPTION_KEY — exactly 32 cryptographically random bytes encoded as base64 (generate locally using `openssl rand -base64 32`). Keep stable; rotating invalidates sessions.

The API fails closed (503) if storage or the key is absent. Do not expose environment variables via browser build prefixes. No request bodies or upstream credentials are logged by these functions. Do not configure external log drains or instrumentation to capture pairing request bodies, headers or query strings. Prefer a separate preview database/namespace for isolation. A shared Redis database shares its quota and credentials; do not flush it. Use a real HTTPS deployment; the QR's canonical target is https://anidashgo.vercel.app/connect?code=<PAIRING_CODE>.

## Protocol
- POST /api/device-pair/create (same-origin browser only): 201, code, local PNG QR data URI, expiresAt. Browser receives a separate HttpOnly binding cookie. Code is 128-bit random hex, manual entry is case-sensitive lowercase. 
- GET /api/device-pair/session?code=...: 200 pending; only name, coarse browser/OS and expiry. Location is deliberately omitted. 400 malformed/unknown, 410 expired/denied/consumed.
- POST /api/device-pair/approve: accept the Android payload from the supplied contract (code, accounts, sync.schemaVersion=1, client.platform=android). Validate each provider's identity using its official API. Explicit denial is `{"code":"...","approved":false}`, without credentials. 
- GET /api/device-pair/status?code=...: original browser binding required. 202 pending, 200 connected with Secure HttpOnly SameSite=Strict login cookie, 410 expired/denied/consumed, 403 if binding is wrong. Redis Lua atomically creates login and deletes pairing credentials. A nonsecret hashed tombstone remains for 24h, then an old code is unknown. Pairing credentials expire after five minutes; opaque browser sessions expire in 30 days. No process-memory fallback.
- GET /api/device-pair/account returns profiles and allowlisted preferences, never tokens. POST /api/device-pair/anilist proxies official GraphQL using the paired session. Existing MAL data route accepts the cookie for paired calls. POST /api/device-pair/logout deletes the server session.

## Sync scope and limitations
Paired AniList lists and exact Android-compatible shx watch notes use the existing tracker integration. MAL supports anime list/progress with AniList media ID mapping; MAL does not provide exact timestamp handoff. The Android preference snapshot is allowlisted: audio, native source, source kind, supported Hindi fields, quality and subtitle options. Download preferences and device-only data are excluded. Browser HLS quality applies where a matching rendition exists; external iframe players do not expose browser quality/subtitle controls. Hindi preference requires explicit language fallback; no silent language substitution. Some Android sources may be unavailable on the browser. The Android contract does not define ongoing preference updates; the current implementation imports a snapshot at pairing. MAL access token expiry requires re-pairing unless Android OAuth client refresh details are later supplied. Existing direct browser OAuth is unchanged; its legacy token storage is separate from paired login. Do not consider the new paired flow production-verified until real Android approval/denial and tracker account testing are performed.

## Verification
The device pairing workflow exercises actual Redis Lua transitions with mock provider identities and tests concurrent consumption, denial, expiry, wrong browser, no credential exposure and rate limits. A separate job builds the React website. Test live on preview before merging.


## Remote paired-device management (v1)
The existing seven URLs and schemaVersion 1 are unchanged. A native Android approval (no browser Origin or Sec-Fetch-Site header) may return:
```json
{"success":true,"deviceManagement":{"token":"<64 lowercase hex characters>","expiresAt":"<ISO-8601 timestamp>"}}
```
Older apps can ignore the optional object. Denial returns only success and never issues a token. Store the opaque token in Android secure storage, never in a URL or log. It authorizes only management of devices under the verified tracker identity, not tracker APIs or browser login. The server stores only a SHA-256 hash of the random 256-bit token, and expires it after 30 days. New pairing issues an independent credential; multiple Android clients can manage the same identity. To renew before expiry, POST /api/device-pair/management with the current Bearer token; the old token is atomically invalidated and the new one is returned in the same optional object. DELETE /api/device-pair/management revokes that credential without signing browsers out. After expiry/revocation, pair again. No management credential is returned to browser JS; browser Origin/Fetch Metadata requests cannot rotate or receive one.

- GET /api/device-pair/devices, Authorization: Bearer <management token>. Returns active devices only. Example:
```json
{"success":true,"devices":[{"id":"a48c8a1d-43d1-42c3-9c56-38cba3fb33ad","name":"Chrome on Windows","browser":"Chrome 150","os":"Windows","pairedAt":"2026-11-28T07:00:00Z","lastActiveAt":"2026-11-28T07:10:00Z","sessionExpiresAt":"2026-12-28T07:00:00Z","current":false}]}
```
- DELETE /api/device-pair/devices/<uuid>, same Authorization. Success 200 {"success":true}; repeating a revocation returns success while the record remains in its seven-day retention period. Unknown/foreign IDs return identical 404. Revocation atomically deletes the encrypted browser session and removes the device from the active index. The next authenticated request rejects the revoked cookie, clears it, and the website returns to its profile/login controls.
- For the website Devices panel, the same list/delete routes accept the existing Secure HttpOnly SameSite=Strict paired cookie instead of a bearer credential. DELETE also requires exact same-origin Origin. Browser requests calculate current by matching their authenticated device record; native requests always return false. A supplied invalid bearer never falls back to cookies.
- Errors: 400 malformed pairing request; 401 missing/invalid/expired management credential or browser session; 403 cross-origin mutation or wrong pairing binding; 404 unknown/foreign device; 405 wrong method; 410 expired/denied/reused pairing; 429 rate limit; 503 storage/config failure. Responses contain no session IDs, token hashes, tracker credentials or IP addresses. Rate limiting uses hashed identities and IP-derived HMAC, never raw IP storage. Optional location omitted.
- Identity: verified AniList numeric ID when present; otherwise verified MAL numeric ID, namespaced by tracker and HMACed. A MAL-only pairing and a pairing with both trackers use different canonical identities; no implicit cross-tracker account linking. A paired browser session expires after 30 days. Activity writes occur at most once every five minutes, with a visible-tab heartbeat and tracker requests. Revoked/expired records do not appear in the active list. Listing is bounded to 200 newest active records per identity.
- Database migration: no destructive commands or schema migration; device metadata, session mapping, identity sorted index and hashed management tokens use new Redis keys under an environment-specific namespace derived from the existing encryption key. Existing paired cookies retain their original TTL and lazily acquire a device record on their next authenticated request. Their paired date is inferred from remaining TTL; browser/OS comes from that request. Old direct OAuth accounts are unchanged and are not paired browser sessions. Older Android approvals can continue pairing; Android must update to persist the optional token to manage devices remotely.
- Deployment: use existing writable Upstash REST credentials and DEVICE_PAIR_ENCRYPTION_KEY for both intended environments. Keep each environment's key distinct and stable. Do not flush the shared database. Existing routes and new routes are rewritten through api/auth-config.js (no additional serverless functions). Test with a disposable Redis in CI; never use production for FLUSHDB. Check the live deployment, then pair with a test Android account, list, revoke and confirm a second browser loses access.
